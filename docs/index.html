Document 01

What this is and why it matters

Written so it stands on its own for someone who has never seen the project.

What it does, plainly

Mercury is an LLM inference server I wrote from scratch in PyTorch. It takes HTTP requests, runs a 0.5B-parameter model on one GPU, and streams tokens back. Internally it does the things a production serving engine does: it stores attention keys and values in fixed-size pages instead of one contiguous buffer per request, it recognises when two requests start with the same text and reuses the cached computation instead of redoing it, it keeps a batch of requests in flight and swaps finished ones out for waiting ones every step, and it streams tokens over server-sent events with proper cancellation when a client hangs up.

But the server is not the point. The server is the instrument.

The point is an experiment. Mercury implements three request-scheduling policies that are identical in every way except the order in which they admit waiting requests, and it measures what that order is worth. The question it answers is:

When the KV cache cannot hold every shared prefix at once, does ordering requests by cache affinity beat first-come-first-served — and what does it cost the requests that get pushed back?

Everything else in the repository exists to make that question answerable with numbers nobody can wave away.

The real problem

Serving an LLM is a memory problem before it is a compute problem.

Every token a model has already seen leaves behind a key and a value vector in every layer. For Qwen2.5-0.5B that is about 12 KB per token. A 2,000-token system prompt costs 24 MB of GPU memory, and it costs that again for every request carrying it, unless you do something about it. The "something" is prefix caching: notice that a hundred requests share the same 2,000-token preamble, compute it once, and let them all point at the same physical memory.

This matters because of how people actually use models now. A chatbot deployment has one system prompt shared by every user. An agent framework sends a tool catalogue thousands of tokens long on every single call. A multi-turn conversation resends its entire history every turn, so turn seven is turn six's prompt plus a bit. Shared prefixes are not an edge case; they are most of the tokens.

Prefix caching is well understood and every serious engine has it. Here is the part that isn't settled. The cache is finite. When the prefixes that are live in your workload add up to more than the cache can hold, the cache has to evict something, and what order you serve requests in decides what gets evicted.

Serve requests strictly in arrival order and you interleave prefix groups: a request for group A, then B, then C, then A again. By the time the second A arrives, A's prefix has been evicted to make room for B and C, so you recompute it from scratch. Then you evict it again for the next B. The cache is full the whole time and almost never useful. That is thrashing, and it is not a subtle effect — in my own measurements it takes the hit rate from 82% down to 45%.

Group the requests by prefix instead and you stop paying for that. That policy exists; SGLang ships it as --schedule-policy lpm. And it has a problem its users have reported: if you always prefer the request with the longest cached prefix, a request whose prefix isn't cached can be displaced by every cache-hot arrival, forever. Someone waits indefinitely so that everyone else can be slightly faster. The fix is obvious in outline — let a request's priority grow as it waits, and put a hard ceiling on the wait — but the interesting question is what that fix costs. Nobody publishes that number.

Mercury measures it.

Why this is harder than it sounds

The memory system and the scheduler are one system

You cannot design the scheduler without the allocator, because "can this request be admitted?" is a question about free blocks, cached blocks that would be pinned, and blocks the running batch will need on the next step. And you cannot design the allocator without the scheduler, because the order blocks are released in determines which ones get evicted. One line in my allocator — the loop that releases a finished request's blocks in reverse order, so its private tail enters the eviction queue before its shared head — measurably changes the hit rate. That line only makes sense if you are holding both halves in your head at once.

Being wrong is silent

The failure that defines this domain

If the block table points at a page that was evicted and handed to another request, the model does not crash. It reads whatever is in that memory, attends over it, and produces fluent, grammatical, completely wrong text. If rotary position embeddings restart at zero for a suffix resumed on top of a cached prefix, the output looks plausible and drifts. There is no exception, no stack trace, no failing assertion.

The only defence is a correctness gate you build deliberately: Mercury compares its greedy output against HuggingFace transformers on the same weights across four modes — single request, batched, with a warm prefix cache, and after a forced preemption — because a prefix-cache bug shows up in exactly one of those and nowhere else.

The effect is conditional, so measuring it means controlling a variable most benchmarks ignore

Prefix-aware scheduling should do nothing when the cache is big enough to hold everything, because then FCFS already hits on almost every request. It should matter in a band where the working set exceeds capacity, and it should stop mattering again when the working set exceeds capacity so badly that even perfect grouping can't keep prefixes resident. A benchmark that reports one number from one configuration cannot tell you which of those three regimes it was in, which means it cannot tell you whether the number generalises. So Mercury's main figure has cache pressure on the x-axis — the ratio of shared prefix tokens live in the workload to KV cache capacity — and sweeps it from 0.25 to 4. The shape of that curve is the finding. A flat left half is not a disappointing result; it is the control that makes the middle believable.

The cost is invisible in the metrics people report

Mean latency, p95 latency, and throughput all improve or stay flat under a policy that starves a minority of requests, because the starved requests are a minority. You only see it if you go looking: maximum queueing delay, measured server-side as the gap between a request arriving and being admitted. That metric is in Mercury because the thing it measures is the reason the policy is controversial.

What makes this different from a tutorial build

I want to be exact about this, because "I built an inference server" is a sentence a lot of people can say, and most of what they built is a wrapper.

The prior art is stated up front, not discovered by the reader

Prefix-aware scheduling is not mine. SGLang shipped it. The starvation problem is a known open issue. A 2026 paper called Feather already measured that prefix-aware schedulers can burn CPU comparable to their GPU work. All of that is in the README's second paragraph. What is mine is the measurement of when it helps as a function of pressure, the aging variant with a hard bound, and the honest accounting of what the bound costs. Claiming to have invented what SGLang already ships is how a portfolio project gets laughed out of an interview.

Every number is explainable down to the allocator

Nothing here is a call into a library I can't read. The paged attention, the block allocator, the hash chain that establishes prefix identity, the scheduler, the continuous batching loop, the Qwen2 forward pass, the safetensors loading, the sampler, the SSE streaming — all of it is in this repository, and when a number moves I can say which line moved it. That is the difference between "vLLM got 2,400 tokens per second" and "the hit rate fell because the release order put the shared prefix into the eviction queue ahead of the private suffix."

The architecture was chosen to be testable, and it is tested

The entire contract between the scheduler and the GPU is one method: execute(plan) -> sampled token ids. Because that seam exists, the allocator, all three policies, preemption, continuous batching, cancellation and the whole HTTP path can be exercised on a laptop with a deterministic fake runner — including randomised property tests that assert reference counts never go negative, that no block is ever in two states at once, and that after thousands of operations every block comes home. The GPU is needed only for parity and for performance. In practice about 40% of the code never needs a GPU, and 94 tests run in under ten seconds on a laptop. I also found a real scheduling insight from those tests rather than from theory: with only one prefix group, all three policies are identical, because there is nothing to thrash between. That is now a test.

The comparisons were pre-registered

Four specific comparisons are written into the README before the experiment runs, including the one designed to fail if the headline is a measurement artifact ("all policies at pressure 0.5 should be within noise; if they aren't, the headline is suspect"). The analysis script computes exactly those four and prints PASS/FAIL. This removes the most common way benchmark projects fool themselves, which is choosing which comparison to report after seeing the data.

Scheduler CPU time is reported, not assumed away

The Feather paper's finding is that prefix-aware scheduling can cost CPU comparable to GPU execution. Mercury times schedule() on every single step and reports it as a share of step time. If the policy wins on hit rate and loses it all to scheduling overhead, that is the result, and I would rather publish it than not know.

What this project is not

It is not a fast inference server. Mercury's attention gathers KV blocks into a padded tensor and calls PyTorch's scaled_dot_product_attention instead of using a fused paged-attention kernel. vLLM will beat it on raw throughput and that is expected and fine — the gather is identical across all three policies, so it cannot bias the comparison that carries the finding. Using it as an excuse to skip the comparison would be dishonest; pretending Mercury competes on absolute speed would be worse.

It is not a new scheduling algorithm. It is a careful measurement of a known one, plus a starvation bound, on hardware anyone can get for free.

It does not run on anything but Qwen2, fp16, one GPU. Those are scope choices, each with a rejected alternative I can defend.

The sentence this is all aimed at

The shape the write-up ends in

On a T4 serving Qwen2.5-0.5B, when shared prefixes exceeded KV capacity by 2×, prefix-aware scheduling with a 5-second starvation bound raised prefix-cache hit rate from A% to B% and cut p95 time-to-first-token by C%, at D% of FCFS throughput, while capping worst-case queueing at E seconds versus F seconds for unbounded LPM; below capacity all policies were within noise.

The last clause is the one that makes the rest believable, and it is the reason the pressure sweep exists at all.

Code walkthrough

How to read this

Plain is the idea with a concrete analogy and no jargon. Technical is the mechanics, the data shapes, and what breaks if it were written differently. If you read only two sections, read the execution trace and the load-bearing blocks.

The shape of the thing

Two halves joined by a queue.

HTTP side (asyncio)                    Engine side (one thread)
-------------------                    ------------------------
FastAPI /v1/completions                schedule -> execute -> route output
  owns sockets, SSE streams,             owns the GPU, the KV cache,
  cancellation                           the block allocator, the scheduler
        |                                        ^
        +------- command queue ------------------+
        <------- per-request sink callbacks -----+

All GPU work lives on one thread. That removes an entire class of concurrency bug — no two threads ever touch the KV cache — and it matches how vLLM and SGLang separate their API server from their engine core. The HTTP side never blocks on the GPU, and the engine side never touches the asyncio loop directly; it calls a per-request sink callback, and the sink is the thing that knows how to hop back onto the right event loop.

One request
1POST /v1/completions arrives; the handler resolves the prompt to token ids and builds SamplingParams.
2It creates an asyncio.Queue and a closure sink(event) doing loop.call_soon_threadsafe(queue.put_nowait, event) — the only bridge from the engine thread back to this stream.
3engine.submit checks the token ceiling, builds a Request — computing its block hash chain here, once, so scheduling never looks at token ids again — and pushes ("add", request) onto the command queue.
4The handler returns a StreamingResponse wrapping an async generator that awaits the queue.
One engine step
1Drain commands. Adds go into the waiting list sorted by arrival; aborts release blocks immediately. Aborts are applied here and nowhere else, so a cancellation never lands in the middle of a forward pass.
2Schedule. Reserve decode blocks for running requests (preempting if memory runs out); score the oldest 128 waiting requests by policy, sort, and admit what fits; return a Plan.
3Execute. One prefill forward per newly admitted request over tokens[num_cached:], one decode forward for the whole running batch, then lm_head and sampling.
4Route output. Commit newly-full blocks into the prefix cache, append the token, call the sink, and close finished streams after releasing their blocks.
5Record. One StepRecord with scheduling time, tensor-prep time, forward time, total step time, queue depths and free blocks.
The stream ending

The generator receives done, emits a final chunk carrying finish_reason, emits data: [DONE], and returns. If instead the client hangs up, the generator is cancelled or request.is_disconnected() returns true; either way its finally fires engine.abort(rid) and the blocks come back on the next step.

hashing.py — what "the same prefix" means

out, parent = [], 0
for start in range(0, len(token_ids) - block_size + 1, block_size):
    parent = block_hash(parent, token_ids[start : start + block_size])
    out.append(parent)
Plain

Imagine numbering the pages of a book, except each page's number is computed from its own words and the previous page's number. Two books get the same number for page five only if they are word-for-word identical through the end of page five. That lets you compare two 2,000-word documents by comparing a handful of numbers, and it means a match on page five is a promise that pages one through five all match.

Technical

A chain hash over full blocks: h_i = H(h_{i-1}, tokens[i*B : (i+1)*B]), so h_i transitively depends on every token before position (i+1)*B. Two consequences the rest of the system leans on. First, a hit on block i guarantees blocks 0..i are shared — which is why cached_prefix_blocks can stop at the first miss instead of scanning. Second, scheduling never touches token ids: hashes are computed once on arrival, so scoring a request for LPM is a handful of dictionary lookups on integers. This is the design the Feather paper argues for over radix-tree traversal, on the grounds that tree walks cost CPU comparable to the GPU work they are scheduling. The loop runs to len - block_size + 1, so a partial trailing block gets no hash — deliberate, because writing the next token into a partial block would corrupt anyone sharing it.

If it were written differently: hashing each block independently rather than chaining would let two requests that share block three but differ in block one collide on block three, and the model would attend over another request's keys. Fluent, wrong output, no error anywhere.

The cryptographic switch

Default is Python's built-in hash over a tuple of ints, which is deterministic across processes (PYTHONHASHSEED randomises strings and bytes, not integers) and fast. The sha256 mode exists because a 64-bit hash over adversarial input is forgeable: a user who could construct a colliding prompt would be served another user's KV. At this scale collisions are negligible; the switch documents that I know why it would matter and what the fix is.

extend_hashes

Plain

The book is still being written. Every time another full page is finished, give it a number, chaining from the last one. Don't renumber the pages you already did.

Technical

Grows an existing chain in place, continuing from hashes[-1]. Called once per step per request. Without it, extending the chain over generated tokens would mean rehashing the whole prompt every step — O(prompt) work per token, which at 2,000-token prompts would dominate the step.

allocator.py — the three-state invariant

The single most important invariant in the codebase: every block is in exactly one of three states.

StaterefHas a hash?Lives in
Free0Nothe free deque
In use≥ 1Once full, yessome request's block table
Cached, evictable0Yesthe evictable OrderedDict, oldest first

Every allocator bug is a violation of that table, which is why check_invariants() exists and why the randomised property test calls it after every single operation.

Plain

Think of a library with identical numbered shelves. A shelf is empty, or someone is using it, or it still holds a book nobody is reading right now but which someone might ask for again. That third state is the whole trick: you don't throw the book out the moment the reader leaves, you keep it until you need the shelf.

plan_prompt — the deliberate refusal to reuse everything

hit = self.cached_prefix_blocks(hashes)[: (num_tokens - 1) // bs]
need_new = -(-num_tokens // bs) - len(hit)
Technical

Read-only, so the scheduler can ask "would this fit?" without side effects. The (num_tokens - 1) // bs cap is not an off-by-one; it is a requirement. If the entire prompt were served from cache, the prefill forward pass would have zero tokens to run and would produce no logits, so there would be nothing to sample the first output token from. Capping the reuse one block short guarantees at least one token is recomputed. vLLM does the same thing for the same reason.

allocate_prompt — the pinning arithmetic

hit, need_new = self.plan_prompt(hashes, num_tokens)
pinned = sum(1 for b in hit if self.ref[b] == 0)
if need_new > self.num_available() - pinned:
    return None
Plain

Before taking new shelves, notice that some of the books you want to reuse are currently on the "nobody's reading it" pile. The moment you claim them, they stop being available for anyone else to clear. So the shelves you can still take is availability minus the ones you're about to claim. Forget that subtraction and you promise the same shelf to two people.

Technical

pinned counts hit blocks currently sitting in evictable with ref == 0. Those are inside num_available(), but claiming them removes them from it. Without the subtraction, a request whose prefix is entirely in the LRU would be admitted when need_new exceeds the truly free count, and _take() would then evict blocks — possibly the very cached blocks this request just pinned, if the pinning hadn't happened first. Ordering matters: hit blocks are pinned before any _take() runs. Returns None with no side effects when it doesn't fit, because LPM skips and tries the next request, and a half-applied allocation would corrupt the pool.

release — the reverse-order line

for b in reversed(blocks):
    self.ref[b] -= 1
    if self.ref[b] == 0:
        if self.hash_of[b] is not None: self.evictable[b] = None
        else: self.free.append(b)
Plain

When a reader finishes, put their books back on the "might be wanted again" pile starting from the last page. The pages at the end are the ones only they were reading; the pages at the front are the shared introduction everybody needs. Since the pile is cleared oldest-first, putting the private ending in first means the private ending is what gets thrown away first, and the shared introduction survives.

Technical

reversed puts the tail blocks into the LRU before the head blocks, so they sit closer to the eviction end. A finished request's last blocks are its private suffix and its generated tokens — content nothing else will ever ask for. Its first blocks are the shared prefix that the next request in the same group needs. Forward-order release inverts that priority and evicts the shared prefix first, which is precisely the thrashing the whole project is about. One keyword, and a real contributor to hit rate.

commit — first writer wins

Technical

Two guards. hash_of[block] is None makes it idempotent, so calling it every step on already-committed blocks is free. h not in by_hash handles duplicate content: two requests can be computing the same block concurrently before either commits. The first becomes canonical; the second stays unhashed, is never shared, and on release goes to free rather than evictable. Trying to merge them would mean rewriting a running request's block table mid-flight, which is a class of bug not worth opening.

scheduler.py — continuous batching and three policies

_preempt — recompute-style

Plain

When the library runs out of shelves, someone has to give theirs up. The person who most recently sat down is asked to leave — but their books go back on the "might be wanted again" pile, not in the bin. When they come back, a lot of what they need is often still there, so restarting is cheaper than it sounds.

Technical

The victim's blocks are released normally, so any committed ones remain in the prefix cache; when it is re-admitted, allocate_prompt may hit most of them and the "recompute" is nearly free. The hash chain is rebuilt over prompt + out because the request now resumes as a longer prompt. Re-inserted by arrival time, so it lands near the front of the waiting queue rather than at the back.

_score — the three policies, and only here

if self.policy == "fcfs":
    return -r.arrival
cached = len(self.alloc.cached_prefix_blocks(r.hashes)) * self.alloc.block_size
if self.policy == "lpm":
    return float(cached)
waited = now - r.arrival
if waited >= self.max_wait_s:
    return float("inf")
return cached + self.aging * waited
Plain

Three ways to decide who gets served next. First: whoever has been here longest. Second: whoever needs the least new work, because their ingredients are already on the counter. Third: the second one, but everyone waiting earns credit as they wait, and anyone who has waited past a hard limit jumps straight to the front no matter what.

Technical

alpha is an exchange rate with units of tokens per second: how many cached tokens one second of waiting is worth. At alpha = 2,000 a request that has waited just over a second outranks a freshly arrived request carrying a 2,000-token cache hit.

There is a subtlety worth knowing, and it is why the hard deadline is not redundant. Two requests both age at the same rate, so a fixed gap in arrival times gives a constant advantage that aging never closes. Aging only wins against arrivals that keep being new — which is the actual starvation scenario, a continuous stream of hot requests. Against any single competitor with a fixed head start, the aging term alone never flips the order. The deadline is what converts "usually fair" into a guarantee. Both of these are tests.

Step 1: reserve decode room, preempt if needed

for r in list(self.running):
    while r.state is RequestState.RUNNING and r.seq_len > len(r.blocks) * bs:
        block = self.alloc.append_block()
        if block is not None:
            r.blocks.append(block); continue
        victim = self.running[-1]
        self._preempt(victim)
decode = list(self.running)
Technical

Termination is the thing to check. Preempting running[-1] either frees blocks from someone else (so the next append_block succeeds, since a running request always holds at least one block) or preempts r itself, which flips its state and ends the while. It cannot spin.

decode = list(self.running) is taken after the preemption loop, so a request preempted this step is correctly excluded from this step's decode batch. Getting that order wrong would run a forward pass over a request whose blocks were just handed to someone else — fluent, wrong output, no error.

Step 2: admission, with three ways to stop and one to skip

PolicyOrder keyWhen a request doesn't fit
fcfsArrival timeStop admitting — strict head-of-line order, like vLLM's default
lpmCached prefix tokens, descendingSkip it and try the next; a smaller or more-cached request may fit
lpm_agingCached tokens + α × seconds waited Skip, unless the request is starving — then stop, so memory frees up for it
The honest limit of the starvation bound

The deadline bounds scheduling delay, not memory delay. Once a starving request outranks everything, admission stops — but it still cannot be admitted until enough blocks free up. The real guarantee is "max_wait_s plus the time for the running batch to release enough memory", and the test asserts that bound rather than pretending it is one step.

Scoring only the oldest 128 is not cosmetic: scoring is O(waiting × prefix blocks) dictionary lookups per step, and the Feather paper's finding is that this can rival GPU time. SGLang caps it the same way. scan_limit_exceeded counts the steps where the queue was deeper than the window, so the write-up can report how often the cap actually bound.

engine.py — the loop and the commit moment

The ceiling check

Plain

If someone orders more than the kitchen could ever cook, tell them now rather than letting them sit in the queue forever.

Technical

A request that cannot fit in an empty pool would be admitted, need a block, find none, preempt the newest-admitted request — itself — and loop forever. Rejecting it at submit turns a hang into a 400. The check is against the pool size and max_model_len, whichever binds first.

_commit_full_blocks — when a block becomes shareable

full = r.seq_len // bs
if full <= r.committed: return
extend_hashes(r.hashes, r.tokens, bs)
for index in range(r.committed, full):
    self.alloc.commit(r.blocks[index], r.hashes[index])
r.committed = full
Plain

A page goes in the catalogue the moment it's completely written, and not a moment before. Catalogue it while there's still room to write and the next word you add will change a page someone else is already reading.

Technical

The timing is exact and it matters. This runs after the runner wrote KV for positions 0..seq_len-1 and before the newly sampled token is appended. At that instant seq_len // bs blocks are completely written, and tokens[0:seq_len] are all known, so the hashes for those blocks can be computed from data that will never change. Commit one step later and you'd hash a block whose last slot hasn't been written — a sharer would attend over uninitialised memory. The committed counter makes it O(new blocks) per step rather than O(all blocks). This is also where generated tokens enter the cache, which is what lets a multi-turn agent's next turn reuse the previous turn's answer.

runner.py and paged attention

slot_mapping — the off-by-one

positions = np.arange(start, stop, dtype=np.int64)
table = np.asarray(blocks, dtype=np.int64)
return table[positions // block_size] * block_size + (positions % block_size)
Plain

Turn "the 37th word of this conversation" into "shelf 9, slot 5". The book's pages are scattered across the library, and this is the index card that says where each one physically lives.

Technical

The decode token's position is seq_len - 1, not seq_len. Using seq_len writes one slot too far, which stays inside the same block for fifteen out of sixteen tokens — so the output is correct for exactly one block and then becomes garbage. The test pins positions 15, 16, 17, 31 and 32 for exactly this reason.

Prefill with a cached prefix

Technical

Three things are doing real work. positions starts at num_cached, not at 0 — rotary embeddings are absolute, and restarting at zero is the single most likely prefix-caching bug, with the symptom that output reads fine and drifts. Only hidden[-1:] is kept, because the vocabulary is 151,936 and only the last position's logits produce a token. And prefill requests are looped one at a time, because prefill is compute-bound so batching them buys little.

paged_decode_attention — the gather

k = k_cache[block_tables].reshape(batch, -1, num_kv_heads, head_dim)
valid = torch.arange(span, device=q.device)[None, :] < seq_lens[:, None]
Plain

Each request's pages are scattered around the library. To do the maths, gather each request's pages into one contiguous stack, pad the stacks to equal height, and mark which rows are real. Then do ordinary attention and ignore the marked-out rows.

Technical

k_cache[block_tables] is advanced indexing, so it copies. That copy is the deliberate trade in this project: a fused paged-attention kernel reads the blocks in place; this gathers them first, costing bandwidth and memory proportional to batch times longest sequence, every layer, every step. It is slower and it is identical across all three scheduling policies, so it cannot bias the comparison that carries the finding. The mask arange(L) < seq_len simultaneously handles the unwritten tail of the last real block and the padding blocks past the end of the table.

paged_prefill_attention — the explicit mask

Plain

Normally "you may only look backwards" is a neat triangle, because the first word you're processing is also the first word of the sentence. But when the first 2,000 words are already cached and you're only processing words 2,001 onwards, the triangle is in the wrong place: word 2,001 may look at all 2,000 before it, not at zero of them. So you write the rule out explicitly instead of using the built-in shortcut.

Technical

is_causal=True assumes queries and keys are aligned at the same origin. With a cached prefix, queries start at num_cached and keys at 0, so the built-in mask would forbid the suffix from attending to the cached prefix at all — and produce output that is grammatical and wrong. The explicit mask is key_pos <= num_cached + query_index. The num_cached == 0 branch is not just an optimisation: at full prefill lengths the explicit mask would be 8000×8000 booleans, 64 MB, for no benefit.

The tied embedding, and why lm_head is None

Technical

Qwen2.5-0.5B ties the input and output embeddings. The obvious implementation — build an nn.Linear and assign lm_head.weight = embed_tokens.weight — breaks under to_empty(), because Module._apply walks each module's own _parameters and would create two separate storages, silently untying them and then failing to load one of them. Not creating the module at all sidesteps the whole problem.

kernels/rmsnorm_quant.py

Why RMSNorm and not an INT4 matmul

On GPUs below compute capability 8.0, Triton's tl.dot falls back to plain FMA on CUDA cores instead of tensor cores. An INT4 matmul written in Triton on a T4 would therefore race cuBLAS's tensor-core fp16 GEMM without tensor cores, and lose, for reasons that have nothing to do with the quality of the code. RMSNorm is a memory-bound reduction with no dot, so it lives on the well-supported part of Triton and the benefit of fusion shows up cleanly.

Plain

In every layer the model does the same three small things back to back: add two vectors, measure the result's size, and divide by it. Done separately, each of those reads the whole vector from memory and writes it back — three round trips for arithmetic that takes no time at all. This does all three while the data is in registers, so the vector crosses the memory bus once.

Technical

BLOCK = next_power_of_2(N) — 896 rounds to 1024, 1536 to 2048 — with a mask so the padding lanes load 0.0 and contribute nothing to the sum or the max. Accumulation is fp32 regardless of fp16 storage. (x * rstd).to(fp16).to(fp32) * w casts to fp16 before applying the weight, matching HuggingFace's ordering, which is what keeps parity tight. Quantisation is symmetric per token with a 1e-6 floor on the scale to prevent a division by zero on an all-zero row — a real case, and a test.

The expected and reported result: the hand-written kernel and torch.compile roughly tied, both well ahead of eager at small row counts where launch overhead dominates, and a single-digit percent end-to-end decode improvement because norms are a small slice of a decode step. "I matched Inductor and measured that it didn't matter much end to end" is a stronger engineering claim than a cherry-picked microbenchmark. The INT8 mode is benchmarked as a component and is not used in production, because Mercury has no INT8 matmul to consume its output.

The benchmark harness

Open loop, and why the whole finding depends on it

Plain

Customers arrive when they arrive. They do not politely wait for the previous customer to leave before walking in. If they did, the queue would never grow, and a project about queue ordering would have nothing to measure.

Technical

One asyncio task per session; each request goes out at its absolute scheduled time regardless of whether earlier ones finished. A closed-loop client with N simulated users caps offered load at what the server can serve, so queueing never builds and the whole scheduling effect vanishes. This is the single most common way serving benchmarks accidentally measure nothing. W3 is the exception by design: a dependent turn waits for the previous request in its session, then sleeps its think time.

In W3, each turn's history uses the trace's scripted assistant tokens, not what the engine actually generated, so every engine sees byte-identical prompts. capacity_for_pressure — the x-axis of the main figure

shared = meta.working_set_tokens / rho
private = max_running * meta.mean_private_tokens
return ceil((shared + private) / block_size)
Plain

Decide how crowded the cache should be. Give it exactly enough room for the shared material divided by how crowded you want it, plus enough elbow room for the requests currently in flight to hold their own private stuff.

Technical

The headroom term is not padding: without it, a high-pressure point starves on private suffixes rather than on shared prefixes, which measures a different phenomenon and would still produce a plausible-looking curve. I got this wrong first time and the symptom was diagnostic — W4's capacity barely moved between pressure 0.5 and 4, because the headroom was computed off the full 4,200-token prompt and swamped the 11,000-token working set.

check_capacity — reading the cap back out

Plain

Ask the engine to use a small cache, then read its own startup message to confirm it actually did. Flags get renamed between releases. If the cap silently didn't apply, every point in the sweep is at the wrong pressure and the resulting figure is beautiful and meaningless.

Technical

Per-engine regex lists against the captured startup log, with a 10% tolerance for engines that round to their own block granularity. Two distinct failures are raised separately: "never reported its capacity" (probably a renamed flag) and "ignored the capacity cap" (reported a number far from the request). Both refuse to run the point rather than producing data.

rate_sweep — finding R_sat first

The rate at which p95 TTFT goes vertical. The matrix then runs at 0.5 and 0.8 of it. Below about 0.3 R_sat the waiting queue is nearly always empty and no policy can reorder anything; above R_sat every policy is dominated by an unbounded queue. The scheduling effect lives in between, and running the matrix without measuring this first is how you get a null result you can't explain.

Tests, and two results that came out of them

94 tests run on a laptop in about ten seconds; 39 more need a GPU. The allocator's three-state table is checked after every single operation across thousands of randomised steps. The cancellation tests run against a real uvicorn socket, because an in-process ASGI transport never delivers http.disconnect — so the test would pass without the cancellation path ever running, which is a test that proves nothing. I found that the hard way.

Document 03

Defending it out loud

For demos, class presentations, and technical interviews. Everything here is meant to be spoken.

The 30-second version

Mercury is an LLM inference server I wrote from scratch in PyTorch — paged KV cache, prefix caching, continuous batching, streaming. But the server is the instrument, not the product. The experiment is this: when the KV cache can't hold every shared prefix at once, serving requests in arrival order makes the cache thrash — you evict a prefix right before the next request that needs it. Grouping requests by prefix fixes that, but it can starve requests whose prefix isn't cached. So I built three schedulers that differ only in admission order, added a starvation bound to the third, and measured what the bound costs as a function of how much cache pressure the system is under. The headline isn't a number, it's a curve: nothing happens below capacity, the policies separate in the middle, and they converge again when nothing fits.

The 2-minute version

Serving a language model is a memory problem before it's a compute problem. Every token the model has seen leaves a key and a value in every layer — about 12 KB per token for the model I used. So a 2,000-token system prompt costs 24 MB, and it costs that again for every request that carries it, unless you cache it. That's prefix caching, and every serious engine has it.

Here's what isn't settled. The cache is finite. When the prefixes live in your workload add up to more than fits, something gets evicted — and the order you serve requests in decides what. Strict arrival order interleaves prefix groups: A, then B, then C, then A again. By the time the second A arrives you've evicted A's prefix to make room for B and C, so you recompute it, and then evict it again. That's thrashing. In my measurements it takes the hit rate from 82% down to 45%, and you can see the mechanism directly in the eviction count, which more than doubles.

Grouping requests by prefix fixes it — SGLang ships that policy. But it has a known problem: if you always prefer the longest cached prefix, a request whose prefix isn't cached gets displaced by every cache-hot arrival, potentially forever. There's an open issue about exactly this. So my third policy adds an aging term — your priority grows as you wait — plus a hard deadline. And the thing I actually measured is what that fairness bound costs in hit rate, because nobody publishes that.

The measurement design is the part I'd defend hardest. The x-axis of the main figure is cache pressure: shared prefix tokens divided by cache capacity, swept from 0.25 to 4. I pre-registered four comparisons in the README before running anything, including one designed to fail if my headline is a measurement artifact — below capacity, all three policies must be within noise of each other. The load generator is open-loop, so queueing actually builds. Output lengths are fixed with EOS ignored, so no engine can look faster by stopping early. And I read the cache-capacity cap back out of each engine's own startup log, because a renamed flag would silently put the whole sweep at the wrong pressure and produce a beautiful, meaningless figure.

What I'm not claiming: that Mercury is fast. My attention gathers KV pages into a padded tensor instead of using a fused paged-attention kernel, so vLLM beats it on throughput. That's fine — the gather is identical across all three policies, so it can't bias the comparison that carries the finding.

The whiteboard version

Draw two boxes and a queue between them. Talk from left to right.

Two halves

All GPU work is on one thread. That kills a whole class of concurrency bug — no two threads ever touch the KV cache — and it's how vLLM and SGLang are structured too. The engine never touches the asyncio loop directly; it calls a callback, and the callback does loop.call_soon_threadsafe. That one line is the whole interface back.

Write: drain → schedule → execute → route

Drain: apply queued submits and aborts. Aborts land here and nowhere else, so a cancellation never arrives in the middle of a forward pass. Schedule: three steps in a fixed order — reserve decode room, preempting the newest-admitted request if the pool is empty; score the oldest 128 waiting requests by policy and admit what fits; hand back a plan. Execute: build tensors, run the forward, sample. Route: append tokens, register newly-full blocks in the prefix cache, close finished streams.

Continuous batching falls out of doing this every step — a finished request's slot and blocks go to a waiting request on the very next step. It isn't a feature, it's what you get for free by scheduling every step instead of per-batch.

Draw a row of numbered boxes

The KV cache is one big preallocated tensor per layer, chopped into fixed 16-token blocks. A request doesn't get contiguous memory, it gets a list of block IDs. So memory can never fragment: any free block serves any sequence. The only waste is internal, the unfilled tail of each sequence's last block, which averages about eight tokens per sequence. That's the answer if someone asks about fragmentation.

Every block is in exactly one of three states: free, in use, or cached-but-unreferenced. That third state is the whole trick.

Chain hashes

Each block's hash is computed from its own 16 tokens and the previous block's hash. So matching on block five is a promise that blocks one through five all match. That means the matched prefix is always contiguous from the start, which is why lookup can stop at the first miss. And it means scheduling never looks at token IDs — hashes are computed once on arrival, and scoring a request is a handful of dictionary lookups on integers.

The one line to point at

When a finished request releases its blocks, it releases them in reverse order. Its last blocks are its private suffix — nothing else will ever want those. Its first blocks are the shared prefix the next request in the group needs. The eviction queue is oldest-first, so releasing backwards means the private tail is thrown away before the shared head. Release forwards and you evict exactly the thing you were trying to cache. It's one keyword and it moves the hit rate.

The three policies differ in one function

_score. FCFS returns negative arrival time. LPM returns cached prefix tokens. LPM+aging returns cached tokens plus alpha times seconds waited, and infinity past a hard deadline. That's it. Everything else — the allocator, the batching, the attention — is byte-identical across the three. That's deliberate: if the only thing that differs is the sort key, then any difference in the results is attributable to the sort key.

The hard questions

On the result itself

Q1Isn't this just SGLang's LPM? What did you actually add?

SGLang's LPM is the second of my three policies and I say so in the README's second paragraph. What I added is three things. First, the measurement of when it helps, as a function of cache pressure — SGLang ships the policy but doesn't publish the curve. Second, the aging variant with a hard bound, which is a proposal on an open SGLang issue that hasn't been measured. Third, the fairness cost stated as a number: how much of LPM's hit-rate gain survives the starvation bound. If you take LPM's number and my aged number, the difference is the price of the guarantee, and that's the contribution.

Q2Your engine is slower than vLLM. Why should I care about your numbers?

Because the comparison that carries the finding is Mercury against Mercury. The three policies share the same allocator, the same attention, the same batching, and differ only in a sort key. Absolute speed cancels out of a within-engine comparison. vLLM and SGLang are in the study as reference points, and specifically SGLang's own FCFS-versus-LPM pair is there as an external check: if my direction of effect disagrees with a production engine's on the same traces, that's a signal I have a bug, and I'd want to know.

Q3How do I know your prefix cache isn't just returning wrong answers quickly?

Parity testing, and it's the exit gate on every milestone. I compare greedy output against HuggingFace transformers on the same fp16 weights across four modes: single request, batched with others, with a warm prefix cache, and after a forced preemption. The requirement is identical first 16 tokens on at least 48 of 50 prompts, plus first-step logits within 1e-2 max absolute difference. Those four modes exist because a prefix-cache bug shows up in exactly one of them — the warm-cache mode — and would pass the other three. In fp16 I don't require exact agreement over long outputs because tiny numeric differences can flip a near-tie, and claiming bit-exactness would be a claim I can't support.

Q4You showed me a fake-runner result. Isn't that made up?

It's a scheduler measurement, not a performance measurement, and I label it that way everywhere. The deterministic runner produces tokens with no model, so nothing about it tells you anything about GPU speed. What it does tell you is what the scheduler does, because the scheduler's inputs are arrival times, prompt hashes and block availability — none of which involve the model. It reproduces the mechanism end to end: six prefix groups against an undersized pool gives FCFS 0.455 hit rate with 1,287 evictions and LPM 0.817 with 576. The eviction count more than doubling is the thrashing hypothesis made visible.

Q5What if you run the real experiment and there's no effect?

Then that's the result, and I have three specific things to check before believing it, in order. One: pressure never actually exceeded 1 — check the capacity cap took effect, which is why the matrix runner reads it back out of the startup log. Two: arrivals were too sparse for any reordering to be possible, because the waiting queue was usually empty and there was nothing to reorder — that's why the rate sweep finds R_sat first and the matrix runs at 0.5 and 0.8 of it. Three: scheduler CPU ate the gain, which is a small-scale replication of the Feather finding and is a publishable result rather than a failure. Each of those is measured, not guessed at.

Q6Your sanity check says all policies should be equal below capacity. What if it fails?

Then my headline is not trustworthy and I say so. That's the entire point of pre-registering it. A failure there means the runs weren't interleaved, or a cache stayed warm from the previous run, or token counts differed between conditions — all measurement bugs, not policy effects. The analysis script prints PASS or FAIL on that comparison specifically so I can't quietly not look.

Q7In your own smoke run, LPM+aging had a worse hit rate than FCFS. Doesn't that sink the whole thing?

It's the most useful number I got, and it's an alpha calibration result rather than a policy result. Here is the run, on the deterministic runner at pressure 2, median of two seeds:

PolicyHit ratep95 TTFT Max queueOutput tok/s
FCFS0.3510.904 s1.231 s 628
LPM0.3760.590 s1.781 s 652
LPM + aging (α 2000)0.2650.666 s 0.963 s642

The fairness half worked exactly as designed — maximum queueing fell from 1.78 s to 0.96 s. The locality half went backwards, and the reason is that alpha is an exchange rate in tokens per second and I had it miscalibrated for that workload. Those shared prefixes were 512 tokens; at alpha = 2,000, one quarter of a second of waiting outweighs a complete cache hit. Cache affinity was swamped almost immediately and the policy degenerated into FCFS plus enough reordering to break the groups up — the worst of both.

So I swept it. Monotone in hit rate and monotone in throughput, which is what a locality-versus-fairness exchange rate should look like. The calibration rule that falls out is alpha ≈ shared prefix tokens / acceptable wait in seconds. For 512-token prefixes and a one-second tolerance that's about 500; for the 2,000-token prefixes in the real experiment it's about 2,000, which is the default the design started with. So the constant was right for the workload it was chosen for and wrong for the one I smoke-tested it on, and the fix is to derive it rather than hard-code it. That's item 4 on the next-version list.

On the systems engineering

Q8Where's your bottleneck?

Two, and I measure both separately. First, the gather in paged attention: k_cache[block_tables] is advanced indexing, so it copies each sequence's entire KV into a padded tensor, every layer, every step. At batch 64 with 2,000-token sequences that's about 32 MB per tensor per layer. That's the dominant cost and it's the thing a fused kernel would remove. Second, per-step tensor building in Python — block tables, slot mappings, sequence lengths, rebuilt every step. At 0.5B a decode step is short enough that this is visible, which is why prepare_seconds is its own metric. Production engines hide it with persistent buffers and CUDA graphs; I don't capture CUDA graphs at all.

Q9What happens under memory pressure — does it deadlock?

No, and there are two guards. At the request level, a prompt plus max_tokens that can't fit in an empty pool is rejected at submit with a 400 rather than queued, because such a request would be admitted, need a block, find none, preempt the newest-admitted request — itself — and loop forever. At startup, the config refuses to start if the whole pool is smaller than max_model_len. Inside the preemption loop, termination is guaranteed because preempting running[-1] either frees blocks from another request, which always holds at least one, or preempts the request being served, which flips its state and ends the loop.

Q10What's your worst failure mode?

A stale block table producing fluent, wrong text. If a block gets evicted and reused while a running request still points at it, the model attends over another request's keys and emits grammatical nonsense with no error anywhere. The structural defence is the reference counting — an in-use block has ref ≥ 1 and is therefore never in the evictable pool — and there's a debug flag that asserts, every step, that every block in every running request's table has ref ≥ 1. The behavioural defence is the warm-cache parity test.

Q11How do you know you don't leak memory?

An end-of-run assertion that available blocks equals total blocks, on every offline test, plus a benchmark mode that cancels 10% of requests at a random point and asserts the pool comes back whole. Leaked blocks from cancelled streams are the classic slow leak in a serving system: nothing looks wrong, and three hours later the pool is empty. I also found that the obvious way to test this doesn't work — an in-process ASGI transport never delivers http.disconnect, so the cancellation path never runs and the test passes for the wrong reason. The cancellation tests run against a real uvicorn socket.

Q12What breaks under bad data?

Adversarial input is the interesting case. I use Python's 64-bit hash over token tuples. A user who could construct a colliding prompt would be served another user's cached KV. At this scale collisions are negligible and I say so, but there's a switch for SHA-256 and the reason it exists is that in a real multi-tenant deployment I'd turn it on. Malformed requests get explicit 400s: empty prompt, batched prompts, a text prompt with no tokenizer loaded, a request past the token ceiling.

Q13Where does this stop scaling?

Several places, in the order you'd hit them. One GPU, no tensor parallelism, so the model has to fit on one card. The scheduler's scan is capped at 128 waiting requests, so past that it degrades toward FCFS by design, and I count how often that binds. The gather in decode attention grows with batch times longest sequence, so long-context plus high concurrency runs out of memory in the gather before it runs out of KV cache. And the per-step Python work is serial with the GPU, so as the model gets smaller and steps get shorter, scheduling and tensor-building become a larger share — which is exactly the Feather finding, and why I report scheduler time as a fraction of step time.

Q14Why one engine thread? Isn't that leaving performance on the table?

Under the GIL, multi-threaded GPU submission from Python buys very little, and the correctness benefit of a single owner for the KV cache is large — no lock discipline to get wrong, no possibility of two threads writing the same block. The real cost is that per-step CPU work sits on the critical path, and I measure that separately rather than hiding it. If I wanted it back, the answer is CUDA graphs and persistent buffers, not more threads.

Q15Your block size is 16. Did you try anything else?

Not as an experiment, and I'd call that a gap rather than defend it. I picked 16 because it's vLLM's default and keeping it identical across engines removes a confounder — if I ran 64 and vLLM ran 16, a reviewer would reasonably ask whether a difference was the policy or the granularity. The tradeoff is understood: bigger blocks mean fewer hash lookups and less gather overhead but coarser sharing and more internal waste. Sweeping it is a next-version item.

Q16How much of vLLM's lead is kernels and how much is CUDA graphs?

That's exactly why the experiment runs vLLM both with and without --enforce-eager. I don't want to attribute a gap to kernel quality when part of it is graph capture that I simply didn't implement. If I'm going to lose to vLLM — and I will — I'd rather be able to say which part of the loss is which.

Q17Isn't fragmentation a problem with a block allocator?

Not external fragmentation — that's the whole point of fixed-size blocks. Any free block serves any sequence, so there's no such thing as a free region too small to use. What you pay instead is internal fragmentation: the unfilled tail of each sequence's last block, which averages about eight tokens per sequence at block size 16. That's the honest answer, and because it's bounded and predictable it's a much easier thing to live with than the contiguous-allocation alternative.

On the measurement

Q18Why open-loop? Everyone uses closed-loop clients.

Because a closed-loop client with N simulated users caps offered load at whatever the server can serve. The queue never grows past N. And this entire project is about the order of the waiting queue — if there's no queue, there's nothing to measure, and all three policies would correctly come out identical. I verified that experimentally, in fact: with a zero-cost fake runner, every request is served instantly, the queue is always empty, and the harness reports no difference between policies. That's the harness being right, and it's the second thing I'd check if the real experiment showed nothing.

Q19Why fixed output lengths? That's not realistic.

It's not realistic and it is necessary. If engines stop at different points, an engine that stops early generates fewer tokens and looks faster, and you're no longer comparing like with like. So every request has a fixed max_tokens with EOS ignored, and the client verifies the streamed token counts and flags any run where they disagree. Realism in output length would cost me the ability to compare at all, and the thing I'm measuring — admission order — doesn't depend on it.

Q20Your warmup sends requests that aren't in the trace. Why not just warm it up with the trace?

Because then the prefix cache would start the measured run already holding the exact prefixes the run is about to ask for, and the first N requests would get free hits they wouldn't get in production. The server does need warming — CUDA context, allocator, Python caches — so the warmup is 50 deliberately off-trace requests, followed by a stats reset. Warm server, cold cache, zeroed counters.

Q21Three repetitions is not a lot. How do you justify any confidence interval?

The three repetitions are different trace seeds, and I report the median across them plus the spread. The confidence intervals come from bootstrapping the pooled per-request values — 500 requests per point, resampled 2,000 times — not from three numbers. And below eight samples the function returns a point estimate with no interval rather than drawing an error bar from nothing.

Q22How do you know thermal throttling isn't your result?

Three things. Run order is shuffled within each session, so if the machine drifts, the drift spreads across conditions rather than landing on whichever policy ran last. GPU clocks, temperature and memory are sampled at 10 Hz for the whole of every run, so I can show they didn't drift rather than assert it. And I can't lock clocks on Kaggle without root, which I state rather than pretend otherwise.

Q23How do you know your client isn't the bottleneck?

I measure it. Client CPU time is recorded per run and reported, and any run where the client exceeded 70% of a core is flagged in the verification output. Kaggle has few cores and the client shares them with the server, so this is a real risk and not a theoretical one. The client is deliberately light — asyncio plus aiohttp, no per-token JSON pretty-printing — and the benchmark sends and receives raw token IDs so there's no tokenizer in the measurement loop.

Q24What stops you from picking the comparison that looks best after seeing the data?

Four comparisons written into the README before the experiment ran, computed verbatim by the analysis script, printed with PASS/FAIL. One of them is designed to fail if the headline is an artifact. That's not a complete defence against motivated reasoning, but it's the standard defence, and the alternative — deciding what to report after looking — is how most benchmark projects fool themselves.

Q25Your max_wait_s is 5 seconds. Where did that come from?

It's a choice, not a derivation, and I'd say so. At 0.5B with these output lengths, a five-second wait is already a bad user experience, so bounding there rather than at one second keeps the bound from dominating the policy entirely. The real answer is that it's a tunable fairness knob and the interesting output is the tradeoff curve, not the point. I have measured that the bound behaves correctly — the starvation test asserts it — and I've measured that tightening it costs hit rate.

Q26What's the actual guarantee your starvation bound gives?

I want to be precise here because the obvious claim is slightly too strong. The deadline bounds scheduling delay: past max_wait_s a request outranks everything and no other request will be admitted ahead of it. It does not bound memory delay — the request still can't start until enough blocks free up. So the honest guarantee is "max_wait_s plus the time for the running batch to release enough memory", and the test asserts that bound rather than pretending it's one step. If I wanted a hard wall-clock bound I'd have to preempt running requests on behalf of a starving one, which is a real design option I didn't take because it trades one unfairness for another.

Known limitations

Stated as facts, because each one was a choice.

  • Qwen2 only, fp16 only, one GPU. No tensor parallelism, no other architectures, no quantised weights. fp16 specifically because a T4 is compute capability 7.5 and has no bf16.
  • No fused paged-attention kernel. The gather is the throughput ceiling. vLLM beats Mercury on raw speed and that gap is mostly this.
  • No CUDA graphs. Per-step launch overhead is paid in full, every step, and measured.
  • No chunked prefill. A long prefill stalls every decode in flight. ITL p99 is reported so the cost is visible rather than averaged away by TPOT.
  • Preemption is recompute-only. No swap to host memory.
  • Block size is fixed at 16 and was not swept.
  • 64-bit non-cryptographic hashing by default. Fine at this scale, not fine against an adversary. The switch exists; the default doesn't use it.
  • Scheduler scan is capped at 128 and degrades toward FCFS beyond that. Counted, not hidden.
  • Synthetic workloads only, and in the multi-turn case the history uses scripted assistant tokens rather than generated ones, which understates caching for agents equally across engines.
  • Single-node measurement on a shared free-tier GPU. Clocks can't be locked. Logged instead.

What the next version adds

In the order I'd actually do them.

  1. A fused paged-attention kernel, or FlashInfer behind the existing context interface. The single biggest absolute-performance item, and the interface already exists to accept it.
  2. Chunked prefill. Mixing a slice of prefill into each decode step removes the ITL spikes that separate prefill phases cause. This is the fix for the metric I currently just report.
  3. CUDA graphs for the decode path, plus persistent buffers so per-step tensor building stops being serial with the GPU. Together with (1), most of the vLLM gap.
  4. Alpha as a function of workload rather than a constant. The smoke run showed alpha has to scale with prefix length; deriving it from the observed mean cached-prefix length would make the policy self-tuning and would remove the one calibration failure I found.
  5. Preemption on behalf of a starving request, so the starvation bound becomes a true wall-clock guarantee rather than a scheduling-order guarantee. This needs a fairness argument about what you're allowed to preempt, which is why it isn't in version one.
  6. A block-size sweep, to replace "I used vLLM's default" with a measurement.
  7. Cryptographic hashing on by default with the performance cost measured, so multi-tenant use is safe out of the box.
  8. Tensor parallelism, which is the point where the single-engine-thread design has to be revisited seriously rather than defended.
